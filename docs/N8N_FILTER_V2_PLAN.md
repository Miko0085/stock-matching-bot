# План улучшения фильтра лидов n8n без изменения архитектуры

## 1. Цель

Повысить полноту обнаружения реальных запросов покупателей и брокеров, не удаляя существующие фильтры локаций, проектов, авторов, стоп-фраз и дублей.

Новый фильтр должен:

- обрабатывать текстовые сообщения на русском и английском языках;
- не выполнять распознавание голосовых сообщений;
- не зависеть от одной точной фразы вроде `cash buyer`;
- отличать запрос на покупку от объявления о продаже;
- не отбрасывать сомнительное сообщение до проверки локации и полного контекста;
- сохранять объяснимую причину каждого решения;
- использовать существующие узлы, соединения, таблицы и каналы отправки n8n.

## 2. Ограничения

Архитектура workflow не меняется. Не добавляются:

- новые webhook-узлы;
- новые очереди;
- новые базы данных или таблицы;
- новые каналы доставки;
- распознавание аудио;
- поддержка языков, кроме русского и английского.

Изменяется только логика существующих Code-узлов и, при необходимости, их конфигурационные значения.

## 3. Текущая архитектура

### DEVI

```text
DEVI Webhook
  -> Config - Telegram Output
  -> Universal Filter + Normalize
  -> Postgres - Save + Dedupe
  -> Keep Only Accepted New Leads
  -> Telegram / Google Sheets / внешняя отправка
```

### Собственные Telegram и WhatsApp workers

```text
Telegram/WhatsApp Webhook
  -> Raw Telegram/WhatsApp -> DEVI Envelope
  -> Raw Monitor Primary Lead Gate
  -> существующие Primary и Secondary ветки
  -> Universal Filter + Normalize
  -> Postgres - Save + Dedupe
  -> Keep Only Accepted New Leads
  -> Telegram / внешняя отправка
```

Эти узлы и связи сохраняются.

## 4. Обнаруженная проблема

`Raw Monitor Primary Lead Gate` сейчас выполняет точный поиск по небольшому списку английских фраз. Сообщение удаляется до проверки локации, если в нём нет одной из заданных формулировок.

По проверенным executions:

- от собственных workers поступило 7 393 сообщения;
- предварительный gate пропустил 58 сообщений;
- 7 335 сообщений, или 99,22%, были отброшены до основного фильтра;
- в результате отправлено только два новых сообщения;
- одно из двух оказалось ложноположительным объявлением о продаже.

Следовательно, точное ключевое слово одновременно:

- теряет реальные запросы с другой формулировкой;
- пропускает объявления, в которых случайно встречается фраза `cash buyer`.

## 5. Роль существующих узлов после улучшения

### 5.1. Raw Telegram/WhatsApp -> DEVI Envelope

Назначение не меняется:

- проверить техническую корректность события;
- привести Telegram и WhatsApp к единому формату;
- сохранить `provider`, идентификаторы, автора, группу, текст и время;
- установить `monitorSource: direct_worker`.

Некорректное техническое событие без `chat_id`, `message_id` или поддерживаемого `provider` можно отклонить на этом этапе.

### 5.2. Raw Monitor Primary Lead Gate

Узел перестаёт быть жёстким exact-keyword-фильтром. Он становится предварительным анализатором с высокой полнотой.

Он должен:

1. Нормализовать русский или английский текст.
2. Определить язык: `ru`, `en`, `mixed` или `unsupported`.
3. Найти положительные и отрицательные сигналы намерения.
4. Добавить результаты анализа в сообщение.
5. Передать текст дальше для проверки локации и полного решения.

Он не должен удалять сообщение только потому, что не нашёл точную фразу из старого списка.

Рекомендуемые поля:

```json
{
  "raw_gate_version": "v2.0",
  "detected_language": "en",
  "positive_signals": ["buyer_demand", "budget", "bedrooms"],
  "negative_signals": [],
  "raw_intent_score": 7,
  "raw_intent_hint": "probable_buyer_request"
}
```

Поля можно хранить внутри существующего `raw_payload` и `decision_meta`. Изменение схемы PostgreSQL не требуется.

### 5.3. Universal Filter + Normalize

Этот узел остаётся главным фильтром. Существующий порядок проверок нужно уточнить:

1. Проверка поддерживаемого источника.
2. Проверка заблокированного автора.
3. Нормализация текста.
4. Проверка сильных стоп-фраз.
5. Проверка локации или проекта по существующему справочнику.
6. Классификация намерения по всему сообщению.
7. Расчёт итогового решения и уверенности.
8. Формирование `decision_meta` и `filter_reason`.

Дедупликация остаётся после фильтра и работает без изменений.

## 6. Нормализация текста

Для русского и английского текста:

- Unicode-нормализация `NFKC`;
- перевод в нижний регистр;
- замена `ё` на `е`;
- замена `.`, `-`, `_`, `/` между словами на пробел;
- удаление повторяющихся пробелов;
- сохранение исходного текста отдельно;
- точные границы слов для коротких сокращений вроде `JVC` и `MJL`;
- разрешение смешанного текста, например `Ищу 2BR in JVC`.

Транслитерация не является обязательной в первой версии. Её можно добавить позже как набор явных alias, не меняя архитектуру.

## 7. Работа с голосовыми сообщениями

Распознавание голосовых сообщений не выполняется.

Правила:

- если у сообщения есть текст или caption, обрабатывается этот текст;
- если сообщение содержит только аудио и не содержит текста, решение — `rejected`;
- причина — `voice_only_not_supported`;
- событие должно остаться видимым в execution и диагностике, а не исчезать без причины.

## 8. Классы намерения

Фильтр присваивает один из классов:

| Класс | Значение |
|---|---|
| `buyer_request` | Человек ищет объект для себя |
| `broker_client_request` | Агент или посредник ищет объект для клиента |
| `seller_listing` | Предлагается конкретный объект на продажу |
| `looking_for_buyer` | Автор ищет покупателя для объекта |
| `advertisement` | Реклама услуг, проекта или подборки объектов |
| `irrelevant` | Сообщение не относится к нужному сценарию |
| `unclear_candidate` | Недостаточно данных для уверенной классификации, но есть подходящая локация или признаки запроса |

## 9. Положительные сигналы

Одна фраза не должна автоматически делать сообщение лидом. Сигналы используются совместно.

### Английский

- `looking to buy`, `looking for`, `need`, `required`, `requirement`;
- `my client is looking`, `client looking`, `buyer looking`;
- `please share options`, `share direct stock`, `send options`;
- `budget`, `up to`, `maximum`, `max budget`;
- `studio`, `apartment`, `villa`, `townhouse`, `bedroom`, `BR`;
- `cash buyer`, `mortgage buyer`, `pre-approved buyer` — только как дополнительный сигнал.

### Русский

- `ищу`, `ищем`, `нужна`, `нужен`, `нужно`, `требуется`;
- `рассматриваю`, `рассматриваем`, `хотим купить`;
- `для себя`, `для клиента`, `клиент ищет`, `есть покупатель`;
- `пришлите варианты`, `поделитесь вариантами`, `предложите`;
- `бюджет`, `до`, `максимальный бюджет`;
- `студия`, `квартира`, `апартаменты`, `вилла`, `таунхаус`, `спальня`.

## 10. Отрицательные сигналы

### Явный поиск покупателя

- `looking for a buyer`;
- `buyer wanted`, `buyers wanted`;
- `cash buyer required` в контексте продавца;
- `ищу покупателя`, `нужен покупатель`;
- `есть объект, ищем покупателя`.

### Объявление о продаже или реклама

- `available for sale`, `unit available`, `direct listing`;
- `for sale by owner`, `exclusive listing`;
- `DM for details`, `call for viewing` без признаков запроса;
- `продаю`, `в продаже`, `доступен к продаже`;
- `эксклюзив`, `листинг`, `звоните для просмотра`;
- длинная подборка объектов, цен и характеристик без фразы запроса.

Наличие `for sale` не является самостоятельным основанием для отказа. Например, запрос `Looking for a studio for sale in Business Bay` является покупательским. Решение принимается по сочетанию запроса, объекта, локации и призыва к действию.

Фраза `cash buyer` также не является самостоятельным подтверждением лида. Она может находиться внутри объявления продавца: `Cash buyer only considered`.

## 11. Правила определения результата

### 11.1. Обязательные условия

Сообщение может пройти фильтр, если:

- техническое событие корректно;
- имеется текст на русском, английском или смешанный текст;
- автор не заблокирован;
- найдена разрешённая локация или проект;
- отсутствует однозначный сильный сценарий `looking_for_buyer`;
- сообщение классифицировано как запрос либо как сомнительный кандидат.

### 11.2. Решения

| Условие | Решение | `filter_passed` |
|---|---|---:|
| Локация найдена, запрос покупателя очевиден | `accepted` | `true` |
| Локация найдена, агент ищет для клиента | `accepted` | `true` |
| Локация найдена, но намерение не полностью ясно | `accepted_review` | `true` |
| Явное объявление продавца | `rejected` | `false` |
| Автор ищет покупателя | `rejected` | `false` |
| Локация не найдена | `rejected` | `false` |
| Только голосовое сообщение | `rejected` | `false` |
| Неподдерживаемый язык | `rejected` | `false` |

`accepted_review` использует существующий маршрут отправки. В Telegram-заголовке необходимо добавить пометку `Требует проверки`, не создавая новый канал или новую ветку.

Так сомнительные сообщения не теряются, но оператор видит, что решение не полностью уверенное.

## 12. Базовая система баллов

Баллы являются стартовой конфигурацией и уточняются после проверки на истории.

### Положительные

- `+5`: явная фраза запроса на покупку;
- `+4`: агент или клиент явно ищет объект;
- `+3`: просьба прислать варианты или прямой stock;
- `+2`: указан бюджет;
- `+2`: указано количество спален или тип объекта;
- `+1`: указан срок, срочность, ипотека или готовность к сделке;
- `+1`: найдены дополнительные конкретные критерии.

### Отрицательные

- `-8`: явная фраза `looking for a buyer` или её русский эквивалент;
- `-7`: явный призыв купить выставленный объект;
- `-5`: структура массовой подборки листингов без признаков запроса;
- `-3`: рекламный призыв написать или позвонить без покупательского контекста;
- `-2`: большое количество объектов и цен без формулировки потребности.

### Предварительные пороги

- итоговый балл `>= 5`: вероятный запрос;
- итоговый балл от `1` до `4`: `unclear_candidate`;
- итоговый балл `<= 0`: вероятное предложение или нерелевантное сообщение.

Локация проверяется отдельно и не должна повышать intent-score: упоминание `Business Bay` ещё не означает запрос покупателя.

Сильная отрицательная конструкция `looking for a buyer` имеет приоритет над отдельными словами `looking` и `buyer`.

## 13. Проверка локаций и проектов

Существующая логика точных фраз и alias сохраняется:

- нормализуются пробелы и разделители;
- короткие сокращения проверяются по границам слова;
- поддерживаются разные варианты написания проекта;
- результат сохраняет `matched_location` и `matched_location_alias`.

В текущем workflow настроены:

- Primary: `City Walk`, `MJL`;
- Secondary: `Business Bay`, `JVC`, `Downtown`.

Добавление новых районов и проектов в этой фазе не является изменением архитектуры. Они добавляются в `CONFIG.locationFilter.locations` соответствующего существующего `Universal Filter + Normalize`.

Важно не дублировать проверку локации в `Raw Monitor Primary Lead Gate`: источником истины остаются существующие Universal Filter-узлы.

## 14. Порядок приоритетов

Проверки выполняются в следующем порядке:

1. Некорректное событие.
2. Пустой текст или voice-only.
3. Неподдерживаемый язык.
4. Заблокированный автор.
5. Сильная отрицательная фраза с учётом контекста.
6. Локация или проект.
7. Классификация намерения и score.
8. Итоговое решение.
9. Сохранение в PostgreSQL.
10. Дедупликация.
11. Отправка новых `accepted` и `accepted_review`.

## 15. Объяснимость и диагностика

Каждый обработанный элемент должен получить:

```json
{
  "filter_version": "v2.0",
  "detected_language": "ru",
  "intent_class": "broker_client_request",
  "intent_score": 8,
  "intent_confidence": "high",
  "positive_signals": ["client_request", "budget", "property_type"],
  "negative_signals": [],
  "matched_location": "Business_bay",
  "matched_location_alias": "business bay",
  "filter_passed": true,
  "filter_reason": "buyer_intent_and_location_matched"
}
```

Допустимые причины отказа:

- `invalid_event`;
- `empty_text`;
- `voice_only_not_supported`;
- `unsupported_language`;
- `blocked_author_name`;
- `blocked_author_profile`;
- `looking_for_buyer`;
- `seller_listing`;
- `advertisement`;
- `location_not_matched`;
- `irrelevant_content`;
- `duplicate`.

Не должно оставаться необъяснимого `return []` после технической нормализации события.

## 16. Одинаковая логика для DEVI и workers

DEVI по-прежнему входит через свой webhook, а workers — через свои. Архитектура не меняется.

Однако окончательное решение должно приниматься одинаковыми правилами внутри `Universal Filter + Normalize`:

- одинаковая нормализация;
- одинаковый справочник локаций;
- одинаковая классификация намерения;
- одинаковые стоп-фразы;
- одинаковые причины решения;
- одинаковая дедупликация.

`Raw Monitor Primary Lead Gate` может добавлять предварительные признаки только для собственных workers, но не должен принимать окончательное решение о лиде.

## 17. Защита от повторения найденных ошибок

### Реальный запрос, который должен пройти

Сообщение с `Serious Buyer inquiry`, запросом студии в Business Bay, бюджетом и просьбой поделиться direct stock:

- класс: `broker_client_request`;
- локация: `Business_bay`;
- решение: `accepted`.

### Объявление, которое не должно пройти

Большая подборка объектов на продажу, где внутри встречается `Cash buyer only considered`:

- класс: `seller_listing` или `advertisement`;
- отдельная фраза `cash buyer` не подтверждает спрос;
- решение: `rejected`.

## 18. Тестирование без изменения production-маршрута

### Этап 1. Shadow mode

В существующих Code-узлах добавить константу:

```javascript
const FILTER_MODE = 'shadow';
```

В режиме `shadow`:

- старое поле `filter_passed` продолжает управлять отправкой;
- новый фильтр рассчитывает `new_filter_passed`, `new_intent_class` и `new_filter_reason`;
- результаты сравниваются на сохранённых executions;
- новые решения пока не влияют на Telegram.

Новые узлы и соединения не требуются.

### Этап 2. Проверка истории

Прогнать доступные сообщения за семь дней и вручную разметить репрезентативную выборку:

- настоящий запрос;
- запрос брокера для клиента;
- объявление продавца;
- поиск покупателя;
- реклама;
- нерелевантное сообщение;
- сомнительный кандидат.

Обязательно включить:

- оба ранее отправленных сообщения;
- сообщения, которые старый gate отклонил;
- русский, английский и смешанный текст;
- Primary и Secondary локации;
- Telegram и WhatsApp;
- повторные сообщения для проверки дедупликации.

### Этап 3. New mode

После проверки изменить только константу:

```javascript
const FILTER_MODE = 'new';
```

Новая логика начинает управлять существующим `filter_passed`. Маршрут после Code-узла остаётся прежним.

## 19. Метрики качества

Главная метрика — recall: доля реальных запросов, которые фильтр не потерял.

Минимальные показатели перед включением:

- recall реальных запросов: не ниже 95% на размеченной выборке;
- 100% решений имеют `filter_reason`;
- 100% принятых сообщений имеют найденную локацию или проект;
- `looking_for_buyer` не попадает в лиды;
- объявление не становится лидом только из-за `cash buyer`;
- одинаковый текст получает одинаковое решение независимо от источника DEVI/worker;
- дубли не отправляются повторно.

Дополнительно считать по каждому источнику:

```text
received
normalized
unsupported_language
location_matched
buyer_request
broker_client_request
accepted_review
seller_listing
rejected
duplicate
sent
```

Статус execution `success` не считается показателем качества фильтра.

## 20. Версионирование и откат

Перед изменением:

1. Экспортировать текущую версию workflow.
2. Зафиксировать текущий `versionId`.
3. Установить `filter_version: v2.0` в новых решениях.
4. Сначала использовать `shadow`.
5. После проверки активировать `new`.

Для отката достаточно вернуть предыдущую версию Code-узлов или переключить `FILTER_MODE` обратно на `legacy`. Схема данных и архитектура при этом не меняются.

## 21. Итоговая рекомендуемая логика

```text
Получить текстовое сообщение
  -> проверить технические поля
  -> определить ru/en/mixed
  -> нормализовать текст
  -> собрать положительные и отрицательные признаки
  -> проверить автора и сильные стоп-фразы
  -> проверить разрешённую локацию/проект
  -> определить buyer/broker/seller/advertisement/unclear
  -> принять, отклонить или пометить "требует проверки"
  -> сохранить решение и объяснение
  -> выполнить существующую дедупликацию
  -> отправить только новый принятый результат
```

Ключевой принцип: ключевые слова являются признаками, а не окончательным решением. Окончательное решение принимает существующий Universal Filter по сочетанию намерения, контекста и разрешённой локации.

- старое точное сопоставление сохранено в диагностических полях;
- решения v2 и причины сохраняются в `decision_meta`;
- существующие фильтры локаций, авторов, стоп-фраз и дедупликация сохранены;
- уведомления используют собственный источник вместо подписи DEVI;
- неуверенные кандидаты имеют отдельную пометку `accepted_review`;
- рабочий режим переключён на `new`.

Дедупликация после внедрения v2 использует точный нормализованный текст как
главный признак. Совпадающий текст блокируется независимо от Telegram-чата,
WhatsApp-группы, имени переславшего пользователя и наличия извлечённых ключевых
слов. Если проверка текста отключена, остаётся прежнее сравнение по выбранным
метаданным; пустое необязательное поле больше не отменяет всю проверку.

Дополнительное усиление от 8 сентября 2026 года:

- `accepted_review` сохраняется в Postgres, но не отправляется как готовый лид;
- `GOOD PRICE`, `URGENT SALE`, `DISTRESS SALE/DEAL`, `I am covered`,
  `I am owner`, `Asking:`, `full payment`, `currently rented` и аналогичные
  русские предложения объекта имеют приоритет продавца;
- денежная цена отделена от явного поля `budget`;
- `Need quick exit` больше не считается запросом покупателя;
- сервисные запросы вроде поиска мастера или танцевальной студии исключаются;
- near-duplicate fingerprint игнорирует служебные пометки владельца/покрытия,
  Telegram/WhatsApp-ссылки, UAE-телефон и пунктуацию;
- повтор с другим чатом, автором или добавленным контактом блокируется до
  уведомления.

На исторической выборке из 8 694 сообщений фильтр оставил 19 событий — 13
уникальных точных текстов. Все просмотренные принятые примеры являются запросами
покупателей или брокеров; `accepted_review` в целевых локациях отсутствует.

Историческая проверка последней доступной выборки обработала 6 492 сообщения.
После фильтра локаций v2 оставил 17 срабатываний, включая повторы одинаковых
запросов. Просмотренные срабатывания являются запросами покупателей или
брокеров; обнаруженные рекламные подборки, объявления и продажа базы
собственников добавлены в регрессионные тесты и больше не проходят.
