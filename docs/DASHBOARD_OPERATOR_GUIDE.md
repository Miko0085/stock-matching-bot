# Пошаговая инструкция: настройка матчинг-сервиса через дашборд

Дашборд: `http://localhost:8094` (или адрес сервера, если развёрнут не локально).
Аутентификация: если `DASHBOARD_USERNAME`/`DASHBOARD_PASSWORD` не заданы в `.env`,
дашборд открыт без пароля — держите его только во внутренней сети.

Каждый раздел ниже помечен:
- ✅ **Работает прямо сейчас** — реально влияет на живой трафик.
- 🚧 **Каталог/задел на будущее** — сохраняется в БД, но пока не читается пайплайном.

Это разделение проверено по коду (не по описанию), чтобы инструкция не вводила
в заблуждение.

---

## 1. Channels (`/channels`) — аккаунты Telegram и WhatsApp ✅

Здесь управляются САМИ аккаунты, через которые идёт мониторинг.

### 1.1 Посмотреть текущие аккаунты
Открыть `/channels`. Для каждого провайдера (Telegram / WhatsApp) отдельная карточка
со списком аккаунтов, статусом (`connected` / `requires_auth` / ...) и, если стоит
пауза — бейджем **"monitoring paused"**.

### 1.2 Подключить новый аккаунт Telegram
1. В карточке Telegram, в поле внизу "Add / connect account" ввести новый
   `account_id` (латиница/цифры/`_`/`-`, например `tg_second`).
2. Нажать **"Add / connect account"**.
3. Обновить страницу (`⟳ Refresh status` вверху) — появится QR-код.
4. В Telegram: **Настройки → Устройства → Привязать устройство** — отсканировать QR.
5. Если аккаунт требует пароль 2FA — появится поле, ввести пароль и нажать "Submit".
6. После успешного входа аккаунт покажет `status: connected` с кнопками "Pause
   monitoring" и "Log out".

### 1.3 Подключить новый аккаунт WhatsApp
Аналогично: поле "Add / connect account" в карточке WhatsApp → отсканировать
QR через WhatsApp → **Связанные устройства → Привязать устройство**.

### 1.4 Поставить аккаунт на паузу (не логаутясь)
Кнопка **"Pause monitoring"** у подключённого аккаунта. Сессия остаётся
подключённой, но входящие сообщения перестают обрабатываться и пересылаться —
ни в матчинг, ни куда-либо ещё. Переживает перезапуск воркера. Возврат —
кнопкой **"Resume monitoring"**.

Используйте это, если нужно временно "заглушить" аккаунт (например, второй
аккаунт дублирует те же группы), не теряя сессию и не нужно логиниться заново.

### 1.5 Выйти из аккаунта (logout)
Кнопка **"Log out"**. Это отличается от паузы: сессия аннулируется на стороне
Telegram/WhatsApp, для повторного использования аккаунта нужен новый вход
(QR заново). Каналы, маршрутизация и история матчей в БД не затрагиваются —
логаут воркеров не имеет доступа к БД вообще.

## 2. Sources (`/sources`) — каталог и маршрутизация групп/каналов ✅

**Обновлено 27.09.2026:** переключатели `Monitoring ON/OFF` и маршрут
`DUBAI / RF / SAUDI / BOTH / AUTO / NONE` теперь **реально управляют пайплайном**.
`dubai-lead-matching-service` перед обработкой любого входящего сообщения смотрит
в `ingest.sources` + `ingest.source_routes` (по `provider + account_id +
chat_id`) и решает:

- нет строки в каталоге вообще → сообщение отклоняется (`source_not_catalogued`);
- `Monitoring OFF` → отклоняется (`source_monitoring_disabled`), даже если
  route выставлен;
- `route = NONE` → отклоняется (`source_route_none`);
- `route = RF` → отклоняется (`source_routed_to_rf_contour`) — этот сервис
  обслуживает только Dubai-контур и никогда не тронет RF-заявку, даже если
  отдельного RF-сервиса пока не существует;
- `route = DUBAI` или `BOTH` → обрабатывается как обычно;
- `route = AUTO` → **временно приравнивается к DUBAI** (реального
  детерминированного классификатора рынка ещё нет — как только он появится,
  это изменится отдельным анонсом).

То есть выключить/включить мониторинг конкретной группы и назначить её
маршрут теперь можно прямо здесь, без API и без перезапуска воркера —
изменение действует на следующее же входящее сообщение.

### Как пользоваться
1. **"⟳ Sync Sources"** — подтягивает актуальный список групп/чатов из
   подключённых аккаунтов (`telegram-worker`/`whatsapp-worker`). Повторный
   sync никогда не затирает уже принятое операторское решение по
   monitoring/route — только добавляет новые источники и помечает
   пропавшие как недоступные.
2. У каждой строки — селект route (`DUBAI/RF/SAUDI/BOTH/AUTO/NONE`, применяется
   сразу при выборе) и переключатель мониторинга.
3. Массовое изменение — чекбоксы + селекты "Set monitoring"/"Set route"
   внизу таблицы + кнопка применения к отмеченным строкам.
4. Фильтры по провайдеру/route/monitoring — только для отображения, на
   поведение не влияют.

⚠️ При первом включении гейта (27.09.2026) все 57 источников, которые уже
реально работали через старый статический список `TELEGRAM_MONITOR_CHAT_IDS`
(51 Telegram) / `WA_MONITOR_GROUP_IDS` (6 WhatsApp), были заранее
промаркированы как `UAE` + `Monitoring ON`, чтобы включение не остановило
текущий мониторинг. Любой источник, синхронизированный ПОСЛЕ этого момента
(например, у нового аккаунта), по умолчанию идёт с `Monitoring OFF` / `route
NONE` — его нужно включить вручную здесь, иначе его сообщения просто не
дойдут до матчинга.

Для *первого* вступления в совсем новую группу (которой ещё нет в каталоге)
всё ещё нужен отдельный шаг — API-вызов или скрипт
(`tools/telegram_join_via_worker.py`, см.
`docs/CHANNEL_ACCOUNT_MANAGEMENT.md`) с `monitor: true`, либо просто
"Sync Sources" после вступления и включение здесь.

## 3. Settings (`/settings`) — конфигурация матчинга

**Обновлено 27.09.2026: Live Cutover включён** (`v2_intake_cutover_enabled =
true`, `buyer_signal_policy = REQUIRE_ANY`). Предупреждающий баннер вверху
страницы всё ещё написан в общем виде ("most settings... feed SHADOW") —
не вводитесь в заблуждение, он не обновлялся под текущее состояние; ниже —
актуальный, проверенный по коду список того, что реально живое.

### 3.1 Что реально влияет на живой трафик ✅ (при включённом Live Cutover)

Пока `v2_intake_cutover_enabled = true` (сейчас — да), детерминированный
V2-гейт реально решает, отправлять ли сообщение на AI. Это делает живыми:

- **Раздел 3 "Blacklist"** — правило-фраза/regex здесь = мгновенный отказ,
  ноль вызовов AI.
- **Раздел 4 "Whitelist"** и **раздел 5 "Property Signals"** — считаются
  попадания правил, сравниваются с порогами ниже.
- **Раздел 6 "Buyer Candidate Gate"** — пороги `Whitelist threshold` /
  `Property signal threshold`: сколько попаданий нужно, чтобы сообщение
  дошло до AI. Явные правила в **SEND_TO_AI** здесь же всегда пропускают
  сообщение на AI, независимо от порогов и от `buyer_signal_policy`.
- **Раздел 7 "V2 Intake Gate — Live Cutover"**:
  - Чекбокс **"Live cutover"** — общий рубильник всего вышеперечисленного.
    Выключить в любой момент — мгновенный откат к старому поведению
    (Phase 3, только SHADOW), без отката кода.
  - Селект **"Buyer signal policy"**: `REQUIRE_BOTH` (нужны И whitelist, И
    property-signal) или **`REQUIRE_ANY`** (сейчас активно — достаточно
    одного из двух; временная антикризисная мера от переизбытка ложных
    отказов, см. `docs/MATCHING_V2_PHASE35_GATE_CALIBRATION.md`, не
    постоянная политика).

⚠️ **Перед изменением любого из перечисленного выше** — обязательно сначала
посмотреть `/shadow-gate` (раздел 4 ниже) и убедиться, что новое поведение
не отсекает лишнего на реальном трафике: это уже не безопасный "теневой"
режим, изменения тут действуют сразу после Apply.

### 3.2 Что сохраняется, но НЕ влияет на живой трафик 🚧 (даже при включённом Cutover)

- **Раздел 2 "Deduplication"** (`event_dedup_enabled`,
  `content_dedup_enabled`, TTL) — дедупликация событий и контента в реальном
  пайплайне включена **безусловно, в коде**, эти чекбоксы её не выключают.
- **Раздел 8 "AI"** (`ai_cache_enabled`, `ai_cache_ttl_days`) — кэш
  интерпретаций тоже всегда включён в коде, чекбокс ни на что не влияет.
- **Раздел 9 "Matching"** (`transaction_matching_enabled`,
  `bedrooms_matching_enabled`, `property_type_matching_enabled`,
  `budget_matching_enabled`, `budget_tolerance_pct`) — все эти фильтры
  жёстко зашиты как всегда-включённые в `hard-filters.js`; настройки из БД
  здесь вообще не читаются ни при каком состоянии Cutover. Страница сама
  пишет: *"This page does not change matcher filters yet (Phase 8)"*.

Активный `dubai-lead-matching-service` не использует пороги 70/85 и не создаёт
`STRONG_MATCH`. Сначала он применяет жёсткие фильтры, затем ранжирует только
прошедшие варианты с весами Location 50 / Budget 30 / Bedrooms 15 /
Property Type 5. Балл влияет только на порядок выдачи, а не на решение
MATCH/NO_MATCH. Веса зафиксированы в `src/matching/scoring.js` и через UI не
редактируются. Меблировка в рейтинг не входит: явно указанное требование —
точный жёсткий фильтр. Допуск по верхней границе бюджета по умолчанию 10%
берётся из `MATCH_PRICE_TOLERANCE_PCT`; одноимённая настройка черновика в БД
пока не управляет живым матчером.

### 3.3 Как редактировать настройки (Draft → Apply)

Любое изменение (чекбокс/число/правило) сразу пишется в **черновик**
(`matching.config_draft`) — реальные таблицы не трогаются. Наверху страницы
появится баннер "N pending changes".

1. Внести нужные изменения (чекбоксы применяются сразу при клике, числовые
   поля — кнопкой "Save" рядом).
2. Прокрутить к баннеру черновика, нажать **"Apply"** — только этот момент
   атомарно создаёт новую версию конфигурации и (для чекбокса Live cutover /
   buyer_signal_policy) реально меняет поведение.
3. Если передумали — **"Discard"** вместо Apply, черновик сбрасывается.
4. Раздел 10 "Configuration History" — список всех применённых версий с
   возможностью **Rollback** к любой из них (тоже атомарно).

### 3.4 Правила (Blacklist / Whitelist / Property Signals / Send-to-AI)

В соответствующем разделе — форма "Pattern" (фраза или regex) + приоритет +
описание → "Add rule". Пока Live cutover включён (сейчас — да) — это реальные
правила, они сразу участвуют в решении "отправлять ли на AI" после Apply, а
не только в SHADOW-оценке.

## 4. Shadow Gate (`/shadow-gate`) — контроль V2-гейта

Показывает: сколько сообщений V2-гейт классифицировал бы иначе, чем старый
триаж (прогноз), и, пока Live cutover включён (сейчас — да) — реальную сводку
`Actual` рядом с прогнозной, разбивку расхождений. Используйте эту страницу
как для проверки ПЕРЕД любым изменением в разделе 3.1, так и для текущего
контроля — сколько сообщений реально отсекается гейтом сейчас, без AI.

## 5. Проверка, что всё реально работает

1. `/` (Summary) — общая картина: активный сток, request flow за период,
   разбивка по no-match-причинам.
2. `/requests` или `/history` — конкретные заявки ↔ матчи с деталями.
3. Реальный тест: дождаться (или прогнать через `/channels` → “Add / connect
   account”) сообщения в мониторимой группе — оно должно появиться в
   `/requests` и, если получен `MATCH`, прийти в Telegram-чат брокеров.
   Старые строки `STRONG_MATCH` относятся только к legacy `pilot-v1`.
