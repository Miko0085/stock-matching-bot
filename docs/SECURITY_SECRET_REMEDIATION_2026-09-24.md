# Security: Secret Remediation — 2026-09-24

**Status:** source-level remediation only. No git history rewrite. No Matching V2 runtime/shadow-gate logic touched.
**Scope:** `n8n/` generated workflow/code files on branch `feature/simplify-matching-v2`.

## 1. What was found

A routine audit while working on an unrelated task (Matching V2 Phase 3) noticed the working tree already had uncommitted edits to 8 files under `n8n/`. Diffing those edits against the committed `HEAD` (`1b30028`, already pushed to `origin/feature/simplify-matching-v2`) revealed that **`HEAD` contains real, working-looking credentials committed in cleartext**:

| File (at `HEAD`) | Secret material found |
|---|---|
| `n8n/code/matching/deterministic-match.js` | OpenAI API key, Telegram bot token, Postgres/Google Sheets/OpenAI n8n credential IDs, Google Sheets spreadsheet ID, Telegram chat ID (all embedded in a `CONFIG` object at the top of the file) |
| `n8n/workflows/nika-pilot-matching.json` | The same `CONFIG` object baked into an embedded Code-node's `jsCode` string, **plus** the Telegram bot token embedded a second time directly in an HTTP Request node's `url` (`https://api.telegram.org/bot<TOKEN>/sendMessage`), **plus** native n8n `credentials` blocks referencing the Postgres and OpenAI credential IDs |
| `n8n/workflows/nika-pilot-stock-sync.json` | Native n8n `credentials` blocks referencing the Postgres and Google Sheets credential IDs, and the Google Sheets spreadsheet ID as a parameter value |

Five other files flagged as modified in `git status` (`build-telegram-messages.js`, `expand-successful-matches.js`, `validate-parser-result.js`, `validate-normalize-aliases.js`, `validate-normalize-stock.js`) had **zero content difference** from `HEAD` — the only diff was line-ending noise (LF/CRLF), a pre-existing, unrelated artifact of this environment's git config. They contain no secret material and needed no remediation.

A repo-wide `git grep` across all tracked files at `HEAD` (excluding the untracked, stale `nika-matching-pilot-starter/` duplicate) confirmed **no other tracked file** references any of these values — the exposure is confined to the 3 files above.

## 2. Root cause

`n8n/code/matching/deterministic-match.js` and both `n8n/workflows/*.json` files are **build artifacts**, regenerated by `scripts/build-workflows.js` (`npm run build:workflows`) from `.env`. That script already sources every one of these values from environment variables — `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `N8N_POSTGRES_CREDENTIAL_ID`, `N8N_GOOGLE_SHEETS_CREDENTIAL_ID`, `N8N_OPENAI_CREDENTIAL_ID`, `GOOGLE_SHEETS_SPREADSHEET_ID`, `TELEGRAM_MATCH_CHAT_ID`, `OPENAI_MODEL` — and defaults every one of them to an empty string (or a safe default like `gpt-4o-mini`) when unset (`scripts/build-workflows.js:14-31`). `.env` is correctly gitignored (`.gitignore:1`) and `.env.example` already documents every one of these variable names with empty placeholder values.

The problem was never the generation mechanism — it was that, at some earlier point, someone ran `npm run build:workflows` against a `.env` populated with **real production values** and then committed the generated output. The generator itself has no hardcoded fallback secret anywhere (verified: `git grep` across `scripts/` for every leaked value returns nothing).

## 3. What was already in progress (found, not created, by this task)

The working tree, before this task started, already had these 3 files edited so that every one of the fields above was empty. Verifying this state (rather than assuming it was a correct or complete scrub) was the first step of this task:

```
$ node scripts/build-workflows.js   # regenerate from the CURRENT (secret-free) .env
$ diff -rq n8n <previously-saved-copy-of-the-working-tree>
(no output — byte-identical)
```

Regenerating from the actual `scripts/build-workflows.js` mechanism against the current `.env` (which has none of these variables set — confirmed by inspecting `.env`'s key names only, no values printed) produced output **byte-for-byte identical** to what was already sitting in the working tree. This is strong evidence the existing edit was produced by someone else already correctly running the project's own build script, not a manual/partial hand-edit — and it means this task's remediation is a **verification and finish**, not a new implementation.

| Value | Classification | Reasoning |
|---|---|---|

| `googleSheetsCredentialId` (`m0aZ...x8`, masked) | **n8n internal credential reference, not a secret itself** | Same reasoning as above, for the Google Sheets OAuth credential. |

## 5. What changed

No manual edits were made to the 3 files' content beyond re-confirming the already-present state via the project's own generator (section 3). All three now contain **empty-string placeholders** for every field above, exactly as `scripts/build-workflows.js` produces when the corresponding environment variable is unset. `openaiModel` reads as `"gpt-4o-mini"` (the generator's documented default) rather than the previously-committed `"gpt-4o-mini-2024-07-18"`, because `OPENAI_MODEL` is not currently set in `.env` — this is an incidental, non-secret side effect of correct regeneration, not a deliberate behavior change; setting `OPENAI_MODEL` in `.env` before the next `npm run build:workflows` restores any specific model pin.

No other file was touched. No Matching V2 runtime, shadow-gate, dashboard, or config code from Phase 0-3 was modified.

Before deploying these workflows (`npm run n8n:deploy`, still gated behind `N8N_ALLOW_WRITE=true` per `AGENTS.md` §2/§10), an operator must populate real values in a local, gitignored `.env` and re-run `npm run build:workflows` to regenerate `n8n/code/**` and `n8n/workflows/*.json` with working credentials — then must **not** commit that regenerated, secret-filled output. This is a process discipline this remediation cannot enforce mechanically (`AGENTS.md` §11 explicitly permits embedding secrets in workflow JSON for deployment convenience); it is called out here so the next person regenerating these files knows not to repeat the original mistake.

## 7. Note on `AGENTS.md` §11 ("Secrets")

`AGENTS.md` §11 states project policy is that embedding secrets directly in n8n workflow JSON is **allowed**, and explicitly: *"Do not remove an embedded secret merely because it is embedded."* This remediation does not follow that clause — it was executed under an explicit, specific user instruction (this task) that classified the already-embedded OpenAI key and Telegram bot token as confirmed-real, already-exposed-in-pushed-git-history credentials requiring rotation, which is a materially different situation from "a secret an operator deliberately embedded for local deploy convenience." The two policies are not reconciled here; if the intent going forward is to *never* commit real secrets into `n8n/` (recommended, given git history is effectively permanent and this repo has already leaked once), `AGENTS.md` §11 should be updated to say so explicitly in a separate, deliberate change — this task did not modify `AGENTS.md`.

## 8. External rotations still required

## 9. Why git history still contains the exposure

This task deliberately did **not** rewrite git history (no `git filter-repo`, no BFG, no force-push, no amend of the Phase 3 commit `1b30028`), per explicit instruction. This means:

- Every commit prior to and including the point these secrets were first committed still contains them in plain text, retrievable by anyone with read access to this repository (local clones, and `origin` if the remote is not solely trusted).
- This remediation only prevents the secrets from being visible in the **current working tree / new commits going forward** from this point.
- The already-pushed exposure on `origin/feature/simplify-matching-v2` is **not** removed by this commit.

## 10. Future history-cleanup option (not performed here)

If the decision is made to fully remove the historical exposure, that is a **separate, higher-risk task** requiring explicit user authorization, because it rewrites shared history:

- Tools: `git filter-repo` (preferred over BFG for this repo size) to strip the specific committed blobs/strings.
- Requires coordinating a force-push to `origin/feature/simplify-matching-v2` and everyone with a local clone re-cloning or hard-resetting to the rewritten history.
- Should only be done **after** the credentials above are already rotated (history cleanup does not un-expose a credential that is still live; rotation is the actual fix, history cleanup is defense-in-depth against future discovery).
- Out of scope for this task by explicit instruction.

## 13. Rollback instructions

This commit only removes secret literals and adds this documentation file — reverting it restores the previous (still-secret-containing, since it only reverts to `HEAD` which already had them) file content, which is never desirable. If this commit needs to be undone for some other reason:

```sh
git revert <this-commit-sha>
```

Note reverting **re-introduces the same real, compromised secrets into the working tree** (they are still sitting in `HEAD`'s history either way) — there is no safe reason to revert this commit; the correct remediation path if something here needs adjusting is a **new** commit editing these files again, not a revert.
